# [故障事件] 服务器OOM导致重启

- **日期**：2026-07-21
- **时间**：19:15 - 21:36 (约2小时21分钟)
- **服务器/系统**：ip-10-0-2-192.eu-central-1.compute.internal (AWS EC2 c8g.4xlarge)
- **严重程度**：P1
- **影响范围**：所有运行在该服务器上的服务
- **处理人员**：运维团队

## 事件概述

服务器因内存耗尽触发OOM Killer，导致metabase等关键服务被杀死，CPU系统态占用飙升至75%，服务器无响应，最终手动重启。

## 时间线

| 时间 | 事件 | 操作/结果 |
|------|------|-----------|
| 19:15 | OOM Killer首次触发 | 杀死metabase Java进程(PID 355764, RSS 9.4GB) |
| 20:20 | OOM Killer再次触发 | 杀死metabase Java进程(PID 691951, RSS 9.3GB) |
| ~21:36 | 手动重启服务器 | 服务器恢复正常 |

## 根本原因

### 直接原因
OOM Killer在内存不足时杀死了metabase Java进程

### 根本原因
1. metabase JVM配置`-Xmx10G`，实际占用近10GB内存
2. 服务器总内存仅30GB，还需运行13个Java微服务
3. 所有服务同时启动，内存竞争激烈
4. 未配置Swap作为安全网

### 触发条件
所有服务重启后同时启动，内存需求超过物理内存

### 数据收集方法

| 数据类型 | 命令/工具 | 输出位置 | 说明 |
|----------|-----------|----------|------|
| 历史CPU数据 | `sar -u -f /var/log/sa/sa21` | 终端输出 | 查看重启前CPU使用率 |

| 服务器运行时长 | `uptime` | 终端输出 | 确认重启时间 |

### 关键发现

**发现1**：19:15和20:20两次CPU系统态飙升
- 数据来源：`sar -u -f /var/log/sa/sa21`
- 数据内容：19:15 %system=54.75%, 20:20 %system=75.14%
- 分析结论：内核在处理OOM Killer时消耗大量CPU

**发现2**：metabase Java进程被OOM Killer杀死
- 数据来源：`journalctl --since "2026-07-21 19:10" --until "2026-07-21 19:20"`
- 数据内容：`Out of memory: Killed process 355764 (java) total-vm:13202552kB, anon-rss:9882408kB`
- 分析结论：metabase进程占用约9.4GB内存，超过系统可用内存

**发现3**：服务器重启后14个Java进程同时启动
- 数据来源：`ps aux --sort=-%cpu`
- 数据内容：metabase(23.7%), lts-fin-financing(10.4%), lts-fin-system(10.4%)等
- 分析结论：大量Java进程同时启动导致内存竞争

## 解决方案

### 紧急处理
1. 手动重启服务器，恢复服务

### 长期修复
1. 降低metabase JVM内存配置从10G到4G
2. 降低lts-fin-erp-adapter JVM内存配置从6G到3G
3. 配置4-8GB Swap作为安全网
4. 为Docker容器设置内存限制

## 建议措施

### 短期（1-3天）
- [ ] 修改metabase JVM配置：`-Xmx10G` → `-Xmx4G`
